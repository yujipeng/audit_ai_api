1. 设计思路：性能 + 验纯为什么要一起跑

做 relay 中转评估时通常有两个独立关心点：

  1. 性能 — 首包延迟（TTFT）、总耗时、p95/p99 抖动；
  2. 纯度 — 模型回的是不是被 relay 偷偷换成了别的模型、有没有 prompt 注入、有没有 system prompt 泄漏。
perf-bench 的核心选择是：用同一批响应同时计算两类指标。
每跑一个 round 都流式拿到完整回答，性能模块从流时间戳里算 TTFT，验纯模块直接读这同一段文本检查身份漂移与注入标记。
这样跑 10 次就同时拿到 10 个延迟样本 + 10 份纯度证据，不需要为验纯额外发请求，对 quota 友好。

对应在代码里就是一条调用链：

StreamingClient.stream()
  → StreamResult { ttft, total_time, text, error, ... }
        ├── perf.metrics.summarize_latencies()  → avg / p50 / p95 / p99
        └── perf.purity.analyze_response()       → identities / refusal / language_mismatch / system_prompt_leak / ...

3. 方案 A — 单路测试（最简形式）

当一把 key 只测一个 relay、一个厂商时，用 位置参数 三段式：

python scripts/perf-bench.py <url> <key> <vendor> \
    [--rounds 10] [--prompt "..."] [--output report.html]

实例

# 测 taoken 的 GPT 通路（默认 prompt = 请介绍北京好吃的，rounds=10）
python scripts/perf-bench.py https://taoken.ai sk-7b1fc763... gpt \
    --output reports/taoken-gpt.html

# 测 taoken 的 Claude 通路，3 轮
python scripts/perf-bench.py https://taoken.ai sk-7b1fc763... claude \
    --rounds 3 --output reports/taoken-claude.html

# 等价的 flag 形式
python scripts/perf-bench.py --url https://taoken.ai --key sk-7b1fc763... \
    --vendor claude --rounds 3 --output reports/taoken-claude.html

跑完会输出：

  • reports/<name>.html — 单文件可分享的对比报告
  • reports/<name>.json — 同名 JSON，含每轮明细，方便二次分析

4. 方案 B — 多路对比测试（YAML）

需要一次跑多 endpoint 出一份对比报告时用 YAML：

YAML 模板

test:
  prompt: "请介绍北京好吃的"   # 默认 prompt
  rounds: 10                  # 每个 (endpoint, model) 跑几轮
  concurrency: 1              # >1 时并发批量
  timeout: 30                 # 单请求超时秒数
  max_tokens: 512
  format: openai              # 或 anthropic
  # temperature: 0.7          # 留空 = 不传 temperature 字段（推荐）

# 可选：跨 endpoint 共享的默认模型
default_models:
  - gpt-5.5
  - claude-opus-4-7

endpoints:
  - name: relay-a
    base_url: https://relay-a.example.com
    api_key: sk-aaaaaaaa
    vendor: gpt               # 用 vendor 预设，自动展开成 gpt-5.2/5.3-codex/5.5

  - name: relay-b
    base_url: https://relay-b.example.com
    api_key: sk-bbbbbbbb
    vendor: claude            # claude-haiku-4-5 / sonnet-4-6 / opus-4-7

  - name: relay-a-claude
    base_url: https://relay-a.example.com
    api_key: sk-aaaaaaaa      # 同 relay-a 但走 claude 通路
    vendor: claude

  - name: relay-c-mixed
    base_url: https://relay-c.example.com
    api_key: sk-cccccccc
    models: [gpt-5.5, claude-sonnet-4-6]   # 显式 models 覆盖 vendor

启动

python scripts/perf-bench.py --config perf-configs/your.yaml \
    --output reports/comparison.html

报告里 Side-by-side comparison 一节会把所有 endpoint × model 组合排成一个表，每行带 OK/Total、TTFT avg/p95/p99、Total avg/p95/p99、Purity 标签。

5. vendor 预设：gpt / claude

不同 key 往往只能调用一个厂商。vendor 字段（YAML 或 CLI 第三个位置参数）会自动展开成该厂商的"较新版本代表模型"集合：

vendor展开模型用途
gpt gpt-5.2, gpt-5.3-codex, gpt-5.5 OpenAI 较新 GPT-5 家族
claude claude-haiku-4-5, claude-sonnet-4-6, claude-opus-4-7 Anthropic Claude 4 全档（轻量 / 主流 / 旗舰）

想跑别的模型时，YAML 用 models: 显式覆盖，CLI 用 --model（可重复）。两个都设的话，models/--model 优先级更高。

6. 验纯（纯度检测）做了什么

每条响应都会过下面这套 6 类启发式检测，结果汇成一个 verdict：

检测项触发条件报告中的 issue 名
身份漂移 响应里出现 "I am GPT-5" / "我是通义千问" 之类的带身份锚点的非 Claude/非目标模型自报家门（关键字表 + 锚点正则，避免误杀） identity_leak
System prompt 泄漏 响应包含 You are a helpful assistant、system:、<|im_start|>、[INST]、忽略之前的指令 等模板/越狱标记 system_prompt_leak
Relay 内部 token 漏出 响应里直接出现 OPENAI_API_KEY、Bearer sk-、===SYSTEM=== 等内部敏感字符串 relay_internal_token
语言不匹配 prompt ≥50% 中文，但响应正文 <20% 中文（Claude / GPT 在 relay 异常路由后偶尔会切英文） language_mismatch
拒答 对良性 prompt 出现 I cannot / 抱歉无法 等 refusal
空响应 OK 状态码但正文空（relay 把流截了或上游被 cut off） empty_response

聚合后的 verdict 四档

CLEAN 所有 round 都正常对题、无标记
SUSPICIOUS 有空响应/拒答/语言切换且占多数
INJECTED 出现身份漂移、system prompt 泄漏或 relay 内部 token
FAILED 该模型在该 endpoint 全部 round 都报错（4xx / 5xx / timeout）

注意：FAILED 表示 性能数据不可用（没有任何成功 round 算 TTFT），但 错误信息（HTTP 状态、relay 报文、request_id）仍然完整保留在报告的错误面板里。

7. 性能指标定义

指标含义实现
TTFTTime-To-First-Token：从发请求到 SSE 流里读到第一段非空 content 的秒数time.perf_counter() 抓取，仅成功 round 入样
Total总耗时：从发请求到 [DONE]（或最后一个 chunk）的秒数同上
avg / min / max样本均值与极值—
p50 / p90 / p95 / p99线性插值百分位（与 numpy 行为一致）perf/metrics.py
stdev样本标准差（n-1）—
output_chars响应正文字符数（用来侧面观察是不是被 relay 截断）—

失败 round 不进 TTFT/Total 样本，但会单独计入 success_rate / failed_rounds。 失败超时也会被实测到 timeout 上限那个秒数，但不污染百分位数据。

8. 异常捕获：超时 / 4xx / 5xx 都进报告

每一轮失败都会单独留一条记录，含：

  • HTTP 状态码（0 表示传输层错误，比如 SSL/timeout）
  • 错误正文前 400 字节（HTTP 503: {"error":...,"request_id":"..."}）
  • 已经接收到的部分文本（如果在流中途断开）
  • 所属的 round 序号 / 模型 / endpoint

HTML 报告里展开 Per-round detail 即可看到每一条；X failed rounds 折叠面板会聚合相同错误。

常见类型示例

错误含义处理建议
HTTP 503 no available accountsrelay 上游账号池暂时空过几分钟重试，或换 relay
HTTP 403 token has no access to model X该 key 没有这个模型权限YAML 中给该 endpoint 设一个允许的 models: 子集
HTTP 400 'temperature' is deprecated新模型不接受 temperature 字段本工具默认就不传 temperature，可以无视
timeout: read operation timed outrelay 接受请求但不返回提高 timeout，或确认上游可达

9. 扩展能力

9.1 自定义 prompt

# 单一 prompt
python scripts/perf-bench.py URL KEY gpt --prompt "讲一个简短的笑话"

# 多 prompt 轮换（YAML）
test:
  prompts:
    - "请介绍北京好吃的"
    - "讲一个简短的笑话"
    - "用 Python 写一个二分查找"
  rounds: 9   # round i 用 prompts[i % 3]

# 多 prompt 轮换（CLI）
python scripts/perf-bench.py URL KEY gpt --prompts-file prompts.txt --rounds 12

9.2 批量 / 并发

# concurrency >1 = 同一个 (endpoint, model) 的 N 个 round 并发发送
python scripts/perf-bench.py URL KEY gpt --rounds 20 --concurrency 5

9.3 测试轮数

--rounds N   # 每个 (endpoint, model) 跑 N 次（默认 10）

9.4 测试模型

# 显式覆盖 vendor 预设
python scripts/perf-bench.py URL KEY gpt \
    --model gpt-4o-mini --model gpt-5-codex

# YAML
endpoints:
  - name: x
    base_url: ...
    api_key: ...
    models: [gpt-5.5, claude-sonnet-4-6, deepseek-chat]

10. 输出文件

文件内容用途
<name>.json schema_version=1 的结构化结果，包含每一 round 的原始数据 二次分析、对接 BI / 仪表板
<name>.html 单文件页面，把同上 JSON 嵌入到 window.__BENCH_DATA__ 然后 vanilla JS 渲染 分享给不方便跑 Python 的人，本地直接双击打开

报告分三大区块：

  1. Overview — endpoints 数、组合数、总成功率
  2. Side-by-side comparison — 跨 endpoint × model 的指标 + 验纯 verdict 一览表
  3. Endpoint blocks — 每个 endpoint 一段，含 8 个统计卡片、延迟分布表、纯度问题列表、错误面板、可展开的每轮明细

12. 故障排查清单

  • 为什么所有 round 都 timeout？ 检查 endpoint 是否支持 SSE，curl https://x/v1/models 是否能返回；如果 GET 通但 POST stream 不通，多半是 relay 的上游账号池/路由出问题。
  • 为什么 verdict=FAILED？ 该 (endpoint, model) 没有任何成功 round。看错误面板里的 HTTP 报文；典型是 4xx 权限或 5xx 上游空。
  • 为什么 TTFT 比直接 OpenAI 慢一倍？ Relay 一般会把请求转发给上游再流式回吐，多一跳；某些 relay 还会先把上游响应缓冲完再发流（伪流式），这种情况下 TTFT ≈ Total。
  • 为什么 verdict=INJECTED 但内容看着正常？ 看 issue 列表 — 多半是 system_prompt_leak（响应里漏了模板字符串）或 identity_leak（不该说"我是 GPT"却说了）。
